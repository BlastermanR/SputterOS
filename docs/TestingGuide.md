# SputterOS Testing Guide

SputterOS uses host-native validation so the library can be exercised on a desktop machine without embedded hardware. The current workflow is split across three paths: unit tests, system tests, and standalone example projects.

## Test Overview

| Suite | Scope | Command | Notes |
|---|---|---|---|
| **Unit Tests** | Core logic, kernel tasks, utilities, and OSAL behaviour | `make unitTest` | Built from the unified `tests/` CMake tree |
| **System Tests** | End-to-end integration paths using real SputterOS components | `make systemTest` | Built from the same unified `tests/` tree |
| **Example Projects** | Standalone executable smoke tests under `exampleProjects/` | `make exampleProjects` | Separate build tree |
| **Formal Report** | Regenerates `FormalTestResults.md` and `FormalTestResults.txt` | `make formalTest` | Summarises the latest run |
| **Coverage** | LLVM source-based coverage for host-native tests | `make coverage` | Generates text and HTML reports |
| **Python CLI** | Protocol, transport, and client tests for `sputterctl` | `cd tools/cli && python -m pytest` | Requires `pip install -e ".[dev]"` |

The latest generated [Formal Test Results](../FormalTestResults.md) file in this repository contains the exact counts from the most recent full run.

> Historical note: the older `tests/buildTest/` bare compilation verification tree has been removed. Top-level `CMakeLists.txt` documents that a future mechanism may replace it.

## Quick Start

```bash
# Run unit tests, system tests, and example projects
make test

# Run only the host-native GoogleTest unit suite
make unitTest

# Run only the host-native system/integration suite
make systemTest

# Build and run standalone example executables
make exampleProjects

# Regenerate the formal markdown report
make formalTest

# Clean all generated build trees
make clean
```

### Prerequisites

- C++17 compiler (GCC, Clang, or MSVC)
- CMake 3.14 or newer
- Ninja
- Threading support for host-native builds
- Network access on first configure, unless GoogleTest is already cached locally

## Test Layout

SputterOS currently uses two build trees:

```text
tests/
├── CMakeLists.txt        # unified unit + system test entry point
├── build/                # generated by make unitTest/systemTest/test/formalTest
├── build_coverage/       # generated by make coverage
├── systemTests/          # GoogleTest integration executables
└── unit/                 # GoogleTest unit executables

exampleProjects/
├── CMakeLists.txt
├── build/                # generated by make exampleProjects or make test
├── heartbeat/
├── pingpong/
├── multirate/
├── sensorpoll/
└── lifecycle/
```

The unified `tests/CMakeLists.txt` file fetches GoogleTest once, builds the SputterOS library once, and then adds both `unit/` and `systemTests/` as subdirectories.

## Unit Tests

### Purpose

Unit tests validate isolated behaviour such as:

- command parsing and interlock logic
- task lifecycle and builder validation
- lock-free queue and watchdog primitives
- timing, logging, memory, and utility code

All unit tests run on the host with test doubles from `tests/unit/mocks/` and shared config from `tests/unit/config/TestConfig.h`.

### Current Structure

```text
tests/unit/
├── config/               # TestConfig.h
├── logic/                # CommandParser, InterlockManager, etc.
├── mocks/                # host-native mocks/stubs
├── osal/                 # queue, watchdog, time, task interface tests
├── tasks/                # ControlTask, CommsTask, DiagnosticsTask, SystemBuilder
└── utils/                # PID, ErrorLogger, CLI, MemoryProfiler, etc.
```

### Running

```bash
make unitTest

# Manual runs from the unified build tree
cd tests/build
ctest --output-on-failure --label-exclude "memory|system"

# Optional label filters
ctest --output-on-failure --label-regex logic
ctest --output-on-failure --label-regex tasks
ctest --output-on-failure --label-regex utils
ctest --output-on-failure --label-regex osal
```

### Notes

- `unitTest` uses the unified `tests/build` tree, not a separate `tests/unit/build` directory.
- If you change `Cfg` requirements, update `tests/unit/config/TestConfig.h` so the shared host config stays valid.

## System Tests

### Purpose

System tests validate full integration flows using real SputterOS components rather than isolated mocks. These tests cover interactions such as:

- `SystemBuilder` lifecycle and task registration
- command queue delivery and end-to-end command routing
- interlock and safety-abort pipelines
- diagnostics monitoring and error logging
- timer rollover handling
- multi-core sync and dual-core data flow
- state-machine progression across ticks
- multi-rate scheduled task dispatch and data flow
- IO_PENDING non-blocking I/O coordination
- scheduling stress under extreme load conditions

### Current Structure

```text
tests/systemTests/
├── CMakeLists.txt
├── config/
├── helpers/
├── test_CommandDeliveryPipeline.cpp
├── test_CommandQueueFlow.cpp
├── test_DiagnosticsMonitoring.cpp
├── test_DualCorePipeline.cpp
├── test_ErrorLoggingPipeline.cpp
├── test_InterlockPipeline.cpp
├── test_IoPendingPipeline.cpp
├── test_MultiCoreSync.cpp
├── test_MultiRatePipeline.cpp
├── test_SafetyAbortPipeline.cpp
├── test_SchedulingStress.cpp
├── test_StateMachinePipeline.cpp
├── test_SystemLifecycle.cpp
└── test_TimerRollover.cpp
```

Each source file builds as its own executable, and `gtest_discover_tests()` registers the discovered GoogleTest cases with the `system` label.

### Running

```bash
make systemTest

# Manual run from the unified build tree
cd tests/build
ctest --output-on-failure --label-regex system
```

## Example Projects

The example projects are not part of the unified `tests/build` tree. They live under `exampleProjects/` and build as standalone host executables.

Current examples:

- `heartbeat` — single-core wiring example with a custom pulse task
- `pingpong` — dual-core example using two threads and atomic turn passing
- `multirate` — single-core multi-rate scheduling (100 Hz + 2 Hz + background)
- `sensorpoll` — IO_PENDING non-blocking ADC pattern with simulated hardware
- `lifecycle` — dual-core AMP with kernel state machine observation

### Running

```bash
make exampleProjects

# Manual run
cmake -B exampleProjects/build -S exampleProjects -G Ninja
ninja -C exampleProjects/build
ctest --test-dir exampleProjects/build --output-on-failure
```

These examples act as smoke tests and as reference integrations for wiring `SystemBuilder`, concrete HAL/OSAL adapters, and the `System<Cfg>` tick loop.

## Formal Test Report

### Purpose

The formal report captures a full test run in markdown and plain text so reviewers can inspect the current validation baseline without rerunning the suite immediately.

### Running

```bash
make formalTest
```

Artifacts:

- `FormalTestResults.md`
- `FormalTestResults.txt`

### Report Contents

- environment metadata (OS, compiler, CMake, architecture)
- pass/fail summary for unit tests, system tests, and example projects
- the most recent discovered test counts
- library size for the built static archive
- tail output from each executed suite

## Adding New Tests

### New Unit Test

1. Add a new source file under the appropriate `tests/unit/<layer>/` directory.
2. Register the executable in that layer's `CMakeLists.txt`.
3. Label it with the appropriate suite label (`logic`, `tasks`, `utils`, or `osal`).
4. Run `make unitTest`.

### New System Test

1. Add a new `test_*.cpp` source file under `tests/systemTests/`.
2. Register it with `add_system_test(...)` in `tests/systemTests/CMakeLists.txt`.
3. Run `make systemTest`.

### New Example Project

1. Create a new directory under `exampleProjects/`.
2. Add a `CMakeLists.txt` that produces an executable and registers it with `add_test()`.
3. Add `add_subdirectory(<name>)` to `exampleProjects/CMakeLists.txt`.
4. Run `make exampleProjects`.

## Python CLI Tests

The `sputterctl` Python CLI package at `tools/cli/` has its own pytest suite covering COBS encoding, protocol frame roundtrips, transport abstraction, and client handshake lifecycle.

### Running

```bash
cd tools/cli
pip install -e ".[dev]"     # First time only
python -m pytest tests/ -v
```

### Test Files

| File | Coverage |
|---|---|
| `test_cobs.py` | COBS roundtrip, encode edge cases, decode error handling |
| `test_protocol.py` | CRC16, frame encode/decode roundtrip, payload serializers/deserializers |
| `test_transport.py` | Abstract transport, TCP echo loopback, connect refused |
| `test_client.py` | Handshake lifecycle, command ACK, metrics request, heartbeat |

### Cross-Validation

The Python COBS and CRC16 implementations mirror the C++ `CobsCodec.h` and `Crc16.h`. Both use the same test vectors (all-zeros, trailing-zero, 254/255 byte runs) to ensure interoperability.

## Troubleshooting

### `make test` Fails Partway

`make test` runs `unitTest`, `systemTest`, and `exampleProjects` in sequence. Run them individually to isolate the failure:

```bash
make unitTest
make systemTest
make exampleProjects
```

### GoogleTest Cannot Be Fetched

GoogleTest is pulled via CMake `FetchContent` on first configure. If network access is unavailable, point CMake at a cached checkout or reuse an existing `_deps/googletest-src` directory.

### Unit or System Tests Crash

Run the relevant label subset with verbose CTest output:

```bash
cd tests/build
ctest --output-on-failure --verbose --label-regex system
```

Common causes include forgetting to call `builder.build()` in a test setup, violating non-blocking assumptions in a mock, or letting `TestConfig` drift from the current `ConfigTraits` contract.

### Formal Report Command Name

The current Makefile target is `make formalTest`. Older docs or notes may still mention `make testFormal`; that name is stale.
